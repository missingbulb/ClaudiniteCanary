# Before a deploy

Backend or frontend, feature or bug fix, UI-only patch, formatting tweak, helper refactor: fill
this in, item by item, **in the response that announces the deploy**. The visible tick is the
whole mechanism — pasting the list without honestly answering it is the same as skipping a
failing test: stop, surface the gap, decide together.

## The commands

```bash
cd backend && npx tsc --noEmit
cd backend && gcloud run deploy gym-copilot-backend --source . --region us-central1 --allow-unauthenticated
cd frontend && npm run build && firebase deploy --only hosting
```

`npx tsc --noEmit` is not optional and not covered by the tests: Vitest runs through esbuild,
which skips type errors the Docker build's `tsc` then fails on, three minutes in. Deploy both
sides when the change spans both. Backend takes 3–5 minutes, frontend about 30 seconds; check
`/health` on the backend and load the hosting URL before announcing either.

## The bar

Not "a log fires" — **"the log is rich enough that a reviewer or user can answer a specific
question about what they are seeing on the page from the log alone, without reading code."** A
token `logDecision` with empty `inputs`/`outcome`, added so the traceability gate goes green,
signals coverage while providing none.

## The checklist

```
PRE-DEPLOY CHECKLIST

--- Instrumentation ---

[ ] 1. New code branch / data filter / config resolution / rule? List each with file:line.
[ ] 2. New FR-ID in docs/requirements.md? List them.
[ ] 3. QUESTION-DRIVEN INSTRUMENTATION. For every behaviour change that affects what a
       user sees or what a downstream system receives, write the questions they will ask
       ("why is X at row N?", "why isn't Y in the list?"). Name the FR-ID whose
       logDecision/logEvent answers each. A question with no answer is a gap: close it
       before deploy, or surface it per-gap for a decision.
[ ] 4. SEMANTIC LOG QUALITY, per new log, cited by file:line:
         (a) `fr` matches requirements.md exactly — paste the `npm run trace --prefix
             backend` line showing hasLog=true for it.
         (b) `decision` is a specific branch name, not "computed"/"processed"/"done".
         (c) `inputs` carries every field needed to reproduce the branch, raw AND
             intermediate (for e1RM: topSetWeight and topSetReps, not just estimated1RM).
         (d) `outcome` carries the value the user sees on the page, not an internal boolean.
         (e) For a classification with sibling branches, the log names which rule matched
             and the priority order that broke the tie.
         (f) Paste one real log entry, from a `vi.mocked(logDecision)` assertion or a local
             run. Fewer than ~3 fields in `inputs` is usually a smell.

--- Test coverage ---

[ ] 5. Enumerate every functional or non-functional behaviour this change adds or modifies.
       Scope is deliberately broad: business logic, API shapes, queries, UI rendering, copy,
       number formatting, error handling, validation, config defaults, auth checks,
       performance, caching, retry, observability fields, accessibility, security, jobs,
       infra. The only valid "none" is comment-only, docs-only or a dependency bump, and
       it must be obvious from the diff.
[ ] 6. For each item in 5, cite the test file:line that would fail if it regressed. No test
       for an item → ask explicitly, per item, and get an explicit yes before shipping it.
[ ] 7. OBSERVABILITY-AS-TESTED. For each log from 3/4, cite the test asserting its `inputs`
       and `outcome` shape — `expect(call[0].inputs).toMatchObject({ … })`. An unasserted
       schema loses fields silently in the next refactor.

--- Safety net + post-deploy ---

[ ] 8. Latent gaps you are knowingly not closing. List them so the decision to wait is theirs.
[ ] 9. ANSWER-THE-QUESTION SELF-AUDIT. Before calling it done, run one `scripts/prod-logs.sh`
       query per question from 3. Cite the queries and paste the decision name plus key
       inputs/outcome. An empty return, or one that cannot answer the question, is a
       blocker — not a follow-up.
[ ] 10. POST-DEPLOY REGEN. For any change to recommendation generation (engine.ts,
        recommendation-pipeline.service.ts, applyVolumeFloor, isSessionRegressed): stored
        Firestore recommendations were generated by whichever revision was live AT
        GENERATION TIME and do not refresh on deploy. Ask for a regen, then cite the new
        revision name appearing in a fresh log entry. If the conversation moves on, circle
        back — never claim the fix is verified without that.
```
